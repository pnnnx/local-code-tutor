# Спецификация датасета «объяснение кода» (для дообучения Qwen2.5-Coder-7B)

## Цель
Научить маленькую модель объяснять код **по сути**: назвать механизм языка, объяснить ПОЧЕМУ код ведёт себя так, прямо назвать подвох (или честно сказать, что его нет), указать граничные случаи и показать исправление. Аудитория — студент, который читает чужой или свой код. Всё на **русском**.

Наблюдаемая проблема базовой модели (именно это лечим):
- пересказывает код построчно вместо объяснения механизма;
- не называет замыкания/позднее связывание, момент вычисления значений по умолчанию, ленивость, общие ссылки;
- не говорит про ограничения (хешируемость, порядок, сложность) и не даёт исправления;
- путает факты («список создаётся при первом вызове» — неверно, при `def`).

## Как работать (обязательно)
1. Пишите примеры пачками по ~8–10 в файл `/home/claude/ds/batches/<category>_NN.py` (формат — см. `/home/claude/ds/batches/_example.py`, это ЭТАЛОН стиля и качества — прочитайте его первым).
2. Сначала напишите `code`, затем запустите `python3 /home/claude/ds/tools/build.py <batch> --dry` — он ВЫПОЛНИТ код и покажет реальный вывод. Ответ пишите, глядя на реальный вывод. Никогда не пишите вывод «по памяти».
3. Затем `python3 /home/claude/ds/tools/build.py <batch> --out /home/claude/ds/parts/<category>.jsonl`. Если есть ✗ — пачка не записывается: исправьте и запустите снова. Предупреждения «вода» тоже исправляйте.
4. Повторяйте до нужного количества. В конце: `wc -l /home/claude/ds/parts/<category>.jsonl`.

## Поля примера
- `id`: `<category>-001`, `<category>-002`, … (уникальные, по порядку)
- `category`: ваша категория (ровно как в задании)
- `kind`: `gotcha` (неочевидное поведение) | `output` (что выведет и почему) | `bug` (найди и исправь ошибку) | `explain` (объясни обычный код, подвоха может не быть) | `system` (объясни программу из нескольких функций/классов целиком) | `compare` (чем отличаются два варианта)
- `lang`: `python` | `javascript` | `c` | `cpp` | `java` | `sql` | `none`
- `question`: вопрос пользователя (без кода; код добавится сам в блоке ```). Можно вставить `{code}` в середину вопроса.
- `code`: код, **запускаемый как есть** и детерминированный (без случайности, времени, сети, ввода; если нужен ввод — поле `stdin`). Должен что-то печатать, чтобы поведение было видно. Для java — `public class Main` с `main`. Для c/cpp — полный файл с `main`. Для sql — скрипт sqlite: CREATE/INSERT, затем SELECT (без `;` внутри строк).
- `answer`: ответ ассистента (см. стиль ниже).
- необязательно: `run=False` (только если код принципиально недетерминирован — потоки/время; не злоупотреблять), `fence=False` (код вставлен «как студент скопировал», без ```), `stdin="..."`.

## Стиль ответа (самое важное)
- Начало: 1–2 предложения — что код делает / что выведет (реальный вывод в `обратных кавычках`).
- Затем **жирные мини-заголовки** (не `#`), по смыслу, например: **Механизм — …**, **Почему так**, **Подвох**, **Граничные случаи**, **Как исправить**, **Сложность**, **Как устроена программа**, **Поток данных**. Не все обязательны; используйте те, что нужны.
- Называйте механизм точным термином: замыкание, позднее связывание, область видимости LEGB, изменяемый/неизменяемый объект, ссылка/алиас, поверхностная/глубокая копия, короткое вычисление `and`/`or`, истинность (truthiness), ленивость генератора, исчерпание итератора, MRO, дескриптор, хешируемость, кэш малых целых, двоичное представление float, банковское округление, hoisting, `this`, event loop, микро/макрозадачи, NULL-логика (трёхзначная), неопределённое поведение (UB), распад массива в указатель, autoboxing и т.д.
- Объясняйте «как интерпретатор/компилятор это выполняет» — по шагам, когда это помогает.
- Если подвоха НЕТ — так и напишите («Подвоха здесь нет, код корректный»), и расскажите о сложности/граничных случаях. Не выдумывайте проблем.
- Если есть ошибка или плохая практика — дайте исправленный код в блоке ```.
- Факты должны быть ТОЧНЫМИ (момент вычисления, порядок, сложность, версии Python ≥3.8). Сомневаетесь — проверьте запуском дополнительного кода через `python3 -c` / node / gcc.
- Длина: обычно 100–350 слов; `system` — до 700. Без воды: запрещены «Давайте разберём», «Таким образом», «Надеюсь, это поможет», «В заключение».
- Не пересказывайте построчно очевидное (`import functools — импорт модуля`).

## Дополнение: kind="write" (для категорий аналитики и дашбордов)
- `kind="write"`: пользователь просит НАПИСАТЬ код (анализ данных, график, дашборд). В вопросе — задача и при необходимости описание/пример данных (поле `context`, необязательно). Поле `code` — это РЕШЕНИЕ; build.py его запустит, а в `answer` оно должно входить ЦЕЛИКОМ в блоке ``` (проверяется). Ответ: короткий план решения → код → объяснение ключевых шагов (почему так, а не иначе) → как проверить/расширить.
- Код для write должен сам создавать свои данные (небольшой DataFrame/CSV во временном файле), быть детерминированным и печатать результат. Графики — сохранять в файл (`plt.savefig('chart.png')`, `fig.write_html('chart.html')`), не `show()`.
- Streamlit/Dash-приложения нельзя полноценно запустить: ставьте `run=False` (build.py проверит хотя бы синтаксис). Вычислительную часть по возможности выносите в функции и демонстрируйте отдельными запускаемыми примерами.
- Версии: в окружении pandas 3.x (Copy-on-Write по умолчанию, строковый dtype `str`), у студентов часто pandas 2.x. Если поведение зависит от версии (SettingWithCopyWarning, chained assignment, dtype строк, inplace) — ЯВНО скажите об этом в ответе, не выдавайте одну версию за универсальную.
